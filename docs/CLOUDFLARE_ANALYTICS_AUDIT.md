## What can be distinguished

Cloudflare documents Host, Path, Referrer, device/browser/OS, Site and Exclude Bots dimensions. Use Host = `legislation.utahbug.com`, a stated date range and Exclude Bots = Yes for a human-oriented view. The bot filter improves that view; it does not identify every automation run. Device categories cannot isolate the owner's PC or iPhone from other similar visitors, and there is no documented Codex identity dimension. Referrers can support attribution when supplied; direct/absent or spoofed referrers do not establish a source or a person. [Available dimensions](https://developers.cloudflare.com/web-analytics/data-metrics/dimensions/).

Ordinary HTTP-only source/HTML probes do not execute the client beacon; they can still appear in separate edge traffic logs. Browser tests can execute it and inflate RUM. Blocking collection avoids RUM submissions but does not erase normal edge requests. Do not combine edge request counts with RUM visits or describe either as verified unique people.

## Recommended minimal solution — not implemented

1. Immediately adopt a test-side policy: run routine suites on localhost or GitHub Review. For necessary production browser tests, install context-wide blocking before navigation for the beacon script and both collection endpoints, disallow service workers, and assert zero forwarded analytics requests. A separate explicitly bounded audit may allow the script but intercept collection, as above. Do not rely on a bot filter or `navigator.webdriver` alone.
2. For a dependable in-site owner-device opt-out, obtain owner approval for a manual installation migration. Owner inspects Pages Metrics/Web Analytics and zone Web Analytics rules, disables every automatic injection path, and confirms how the Pages integration removal takes effect on a separately authorized deployment. Merely setting localStorage cannot suppress the current injected script; removing it after execution is too late.
3. In that future approved package, use one small application-owned loader on the exact production hostname, covering the homepage and eligible static pages. It checks a device-local boolean before inserting the existing Cloudflare public beacon snippet. Add an accessible “Exclude this browser from analytics” preference, with opt-in/reload recovery and honest blocked-storage feedback. Do not put a user identifier, secret token, cookie or tracking flag in URLs. Use the existing public site tag; never embed API credentials. Stop on unavailable preference storage rather than claiming persistent exclusion. Keep automatic injection off to avoid duplicates.
4. Owner sets opt-out separately in each PC browser/profile and iPhone browser. It is origin-local, not cross-device identity. Private browsing, clearing site data, other browsers and external in-app browsers require renewed choice. Existing server/edge logs remain unaffected; this is a RUM opt-out only.
5. Validate first in a local fixture with intercepted endpoints: default/opt-out/reload/opt-in, storage failure, all static-page entry points, Chromium/WebKit and actual iPhone. After separately authorized production deployment, verify opted-out pages load no beacon and send no collection requests; a single owner-approved opted-in visit loads exactly one beacon. Owner confirms receipt under the exact Host/date filter. Do not resubmit historic traffic or attempt to identify/remove past owner visits.

This preserves aggregate measurement without visitor fingerprinting or personal identification. A browser-level content blocker is an interim owner-managed alternative, but compatibility, per-browser rules and blocking same-origin endpoints need actual PC/iPhone verification; no paid product is recommended here. IP exclusions are a poor device control because mobile/VPN/shared addresses change or cover other visitors. Cloudflare [Rules](https://developers.cloudflare.com/web-analytics/configuration-options/rules/) operate on hostname/path for proxied sites, not a browser's localStorage value.

Cloudflare Web Analytics is [free](https://developers.cloudflare.com/web-analytics/about/); the proposed loader adds no paid service or recurring service fee. Engineering/maintenance time and owner validation remain costs. Existing account/hosting charges are unchanged. Cloudflare's [FAQ](https://developers.cloudflare.com/web-analytics/faq/) documents six-month access, seven-day unsampled storage followed by aggregation, query-time sampling and omission of query strings. Aggregation, blockers and network loss limit precision; no exact-person or complete-traffic promise is appropriate.

Required owner decisions: inspect current analytics dashboard/rules and totals; accept the manual-loader/device preference approach and wording; authorize configuration and production changes as a separate release. Until then, retain the current beacon unchanged and apply test-side exclusion for audits.
