## Product decisions and acceptance boundaries

Use compact, information-first listings, 44px touch targets, independent visible keyboard focus, accessible announcements, readable enlarged text and locally saved appearance (production/Review direct Light/Dark toggle with safe legacy preference handling; Main retains its existing Device/Light/Dark selector). Keep source links and row navigation distinct. Search, bookmarks, Copy and CSV operate on the full matching set in the selected order. **SHARE-001** covers sharing. Basic local bookmarks implement part of **TRANS-006**. Change monitoring and notifications remain deferred.

Use official evidence and neutral wording. Keep requests distinct from introduced legislation, source observations distinct from verified status, and observation dates distinct from legislative action dates. Describe documented changes without attributing motives or political judgments. Preserve original wording and exact versions for legal comparisons. AI-assisted explanations require independent editorial review before human approval can be claimed. **RELEASE-001** and **UI-001** retain human editorial and accessibility gates. [Editorial review packets](review/README.md) · [Accessibility acceptance](review/ACCESSIBILITY.md).

2. **Making a release:** Build and verify GitHub Main and Review together. A push to GitHub Main triggers the Pages workflow. Cloudflare uses manually approved production-only packages. [Release procedure and rollback](CLOUDFLARE_PRELAUNCH.md) · [Current public indexing procedure](PUBLIC_SEARCH_INDEXING.md).

These local artifacts are outside Git. Use the recorded successful deployment for rollback and verify its homepage, release metadata, indexing policy and checksum. If evidence is unavailable, recover it before an upload.
4. **Maintaining this file:** After substantial approved development or a production release, update the verification date, affected environment/version, source dates, decisions with dates and reasons, evidence links and remaining owner actions.
