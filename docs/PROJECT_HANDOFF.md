## Publication and recovery

1. **Starting a conversation:** Read [AGENTS](../AGENTS.md), this handoff, then the relevant backlog entries, dated verification records and acceptance checklist. Fetch remote Main, inspect local changes and check recent Actions runs and active jobs. For ChatGPT without repository access, ask for this file at a named commit and the relevant evidence. Recheck versions before treating a dated count, deployment or owner approval as current.
2. **Making a release:** Build and verify GitHub Main and Review together. A push to GitHub Main triggers the Pages workflow. Cloudflare uses manually approved production-only packages. Start from the accepted production bytes, verify source identities, dates, file hashes, mandatory CI, project/branch and the previous successful deployment ID. Preserve rollback artifacts. Check the actual custom domain after upload. New code/data promotion, production automation, DNS, analytics, advertising and promotion of Review typography require owner decisions. [Release procedure and rollback](CLOUDFLARE_PRELAUNCH.md) · [Current public indexing procedure](PUBLIC_SEARCH_INDEXING.md).
3. **Finding rollback evidence:** On the release workstation, look under `release-candidates/public-index-<packaging-commit>/` for `site/`, `release-manifest.json`, `SHA256SUMS` and `delivery/`. These local artifacts are outside Git. Use the recorded successful deployment for rollback and verify its homepage, release metadata, indexing policy and checksum. If evidence is unavailable, recover it before an upload.
4. **Maintaining this file:** After substantial approved development or a production release, update the verification date, affected environment/version, source dates, decisions with dates and reasons, evidence links and remaining owner actions. Distinguish implemented, deployed, owner-accepted and pending outcomes. Keep detailed technical history in its authoritative record.
